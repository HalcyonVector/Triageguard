\section{Design and Methodology}

\subsection{Design principles}
Two rules shape the design. (1) \emph{The LLM never sees the raw dump}, only structured findings. This
shrinks the attack surface and keeps every statement traceable to a finding id. (2) \emph{Facts come from
code, not from the LLM.} Cipher confidence, key strength and the risk score are computed
deterministically; the LLM only writes them up and a validator checks that it did so honestly.

\subsection{Architecture}
The code is a Python package (\texttt{triageguard/}) with one module per stage, a SQLite store, a report
layer and a command-line front end (Fig.~\ref{fig:arch}). \texttt{pipeline.py} orchestrates the stages;
each stage is independent, so a missing input (no Windows kernel, no pcap, no API key) skips that stage
instead of failing the run. A local dashboard (standard library HTTP server, localhost only, offline)
reads the exported \texttt{results/} folder.

\subsection{Database design (ER diagram)}
All evidence lives in two tables (Fig.~\ref{fig:er}). A \texttt{run} is one analysis of one dump; it owns
many \texttt{findings}. Each finding has a citation id (\texttt{ref}, e.g.\ F12) that the LLM must cite and the
validator and dashboard resolve. Stage-specific detail is a JSON column, so new checks need no schema change.

\subsection{Modules, algorithms and justification}

\textit{Memory (Volatility3).} The standard open-source framework; it auto-detects the Windows build and
fetches symbols. Raw \texttt{malfind} hits are graded: an \texttt{MZ} header in a region is critical, known
JIT processes and zero-filled regions are low, identical code in three or more processes is a system-wide
component (medium), and unique code in one process is high. Suspicious command lines (encrypt, ransom,
vssadmin, bcdedit) and shells with unusual parents are flagged.

\textit{Static (pefile, YARA).} Applied to extracted regions and supplied binaries: SHA-256, entropy,
ASCII and UTF-16 strings, PE imports and section entropy, and YARA rules.

\textit{Entropy.} Shannon entropy $H=-\sum_b p_b\log_2 p_b$ over a 4\,KB sliding window; windows with
$H\ge7.2$ bits/byte are merged into high-entropy regions. The threshold is the level Lyda and Hamrock
measured for encrypted executables (mean 7.18, packed 6.80)~\cite{lyda2007using}. A random 4\,KB window
measures about 7.955, not 8, because the plug-in estimate is biased low by $(256-1)/(2N\ln 2)$~\cite{miller1955note}.
Entropy cannot separate encrypted from compressed data (in our test, deflate and LZMA output passed a
byte-uniformity $\chi^2$ test as often as random data), so regions are reported as ``encrypted or
compressed''; Casino et al.\ train a classifier for that step~\cite{casino2025not}.

\textit{Cipher identification.} 56 signatures (S-boxes, T-tables, round constants, DES tables, the ChaCha
``expand 32-byte k'' constant, GHASH tables, curve parameters, key-blob headers and API names, in ASCII
and UTF-16), each with a weight $w_i\in(0,1)$. In Dempster-Shafer terms~\cite{shafer1976mathematical},
$w_i$ is the basic probability mass signature $i$ commits to ``$A$ is present'', with $1-w_i$ left on
``unknown''. Combining these simple support functions with Dempster's rule gives no conflict (they all back the
same hypothesis), and the belief in $A$ over the matched signatures $S_A$ is
\begin{equation}
  \mathrm{conf}(A) = \mathrm{Bel}(A) = 1 - \prod_{i\in S_A}(1-w_i),
\end{equation}
the same expression as a noisy-OR. One strong hit counts a lot, weak hits accumulate, and confidence never
reaches 100\%. The masses are analyst-assigned in fixed tiers (0.7 for constants only an implementation or a
live key needs, 0.6 for algorithm-unique tables, 0.5 for tables or names shared with generic libraries,
0.3--0.4 for API names, 0.1--0.25 for short patterns); there is no published table of such weights, and the
rule assumes the signatures are independent. Because belief is monotone over subsets, evidence for AES-GCM
also supports AES: $\mathrm{conf}(\text{AES})$ combines both with the same rule. Each result also
states its \emph{basis}: implementation constants (the cipher is implemented here) or API/string references
only (merely named), because almost every Windows process names AES.

\textit{RSA weak keys.} Keys are carved from CAPI blobs, CNG blobs, DER SubjectPublicKeyInfo and PEM, then
tested for modulus size ($\le$829 bits critical, $<$1024 high, $<$2048 medium), small exponent, shared
modulus, shared prime by pairwise $\gcd(n_i,n_j)$, close primes by Fermat factorisation, and small factors
(trial division, Pollard rho). Strength is measured as NIST security strength $s$ in bits: the SP~800-57
table~\cite{nist80057} for moduli of 1024 bits or more (1024$\to$80, 2048$\to$112, 3072$\to$128,
7680$\to$192, 15360$\to$256, sizes in between taking the lower row), and below that the GNFS cost formula
of FIPS~140-2 IG~7.5~\cite{fips140ig},
\begin{equation}
  E(n) = \frac{1.923\,\sqrt[3]{n\ln 2}\,\big(\ln(n\ln 2)\big)^{2/3} - 4.69}{\ln 2},
\end{equation}
which gives $E(1024)=80.0$, matching the table. $s=0$ when a test recovered the key, for a shared modulus
with a standard second exponent, and for moduli at or below 829 bits, the public factoring record
(RSA-250~\cite{boudot2020comparing}). The 0--100 score is $100\cdot\min(s,128)/128$, the share of SP~800-57's
128-bit target, and each key also gets a status: broken, disallowed ($s<112$, SP~800-131A~\cite{nist800131a})
or acceptable. A small exponent does not lower the factoring cost, so it is reported as non-compliance with
FIPS~186-5 ($e>2^{16}$)~\cite{fips1865} rather than as lost bits. A modulus with a tiny factor is treated as
corrupt memory, not a key.

\textit{Credentials.} JWTs are decoded and checked (\texttt{alg=none} high, HS256 noted, expiry);
OTP secrets under 128 bits (the RFC~4226 minimum) are flagged; all secrets are stored redacted with a short hash.

\textit{Network (pyshark).} Uses Wireshark's dissectors. Only the server's chosen suite and version are
read; RC4, DES/3DES, NULL/export, static RSA key exchange, CBC, SSL~3.0 and TLS~1.0/1.1 are flagged.

\textit{Risk score (evidence fusion).} Every finding becomes a simple support function for ``the host is
compromised or exposed'', with mass $m_f$ equal to the midpoint of its severity's CVSS~v3.1 band divided by
10~\cite{first2019cvss} (critical 0.95, high 0.80, medium 0.55, low 0.20, info 0), times the detector's own
confidence where it has one (cipher ID). Findings from one source (module and kind) are not independent, for
example 37 certificates from one certificate store, so they are combined with Den{\oe}ux's cautious
rule~\cite{denoeux2008conjunctive}, which for simple support functions keeps the largest mass. Independent
sources $S$ are then combined with Dempster's rule:
\begin{equation}
  \mathrm{risk} = 100\Big(1 - \prod_{S}\big(1 - \max_{f\in S} m_f\big)\Big),
\end{equation}
capped at 99 since belief never reaches 1. One critical source gives 95 and two independent medium sources
give 80, so the score falls in the CVSS band of the evidence behind it, and low-severity context cannot pile
up. The rule-based report lists each source's mass, so the score can be traced back to findings.

\textit{LLM report and defences.} Groq's free tier (\texttt{openai/gpt-oss-120b}) through an
OpenAI-compatible API, so any endpoint (e.g.\ local Ollama) can be swapped in. Four defences:
(D1) \emph{sanitise} instruction-like text and forged citations, each hit becoming a high
\texttt{prompt\_injection} finding; (D2) \emph{spotlighting}~\cite{hines2024spotlighting}: findings are marked as
untrusted data between delimiters; (D3) \emph{citation check}: $\ge$90\% of claim lines cited and every id
must exist; (D4) \emph{rule cross-check}: stated risk within 20 points of ours, every critical/high finding
mentioned, every named algorithm present, every confidence and strength figure in the report's tables equal
(within 1 point) to the one computed for the finding the row cites, dismissive or dangerous advice flagged.
The sanitiser normalises text first (NFKC, zero-width characters removed, Unicode TR39
look-alikes~\cite{unicode2023tr39} mapped to Latin) and also scans base64 it can decode. A failing report gets
one retry with the list of problems; if it still fails it ships with a ``Validation notes'' section.
The sequence is shown in Fig.~\ref{fig:seq} (Appendix).

\textit{Why SQLite and Python.} A single-file database needs no server, is easy to export, and gives each
finding a stable id. Python has mature bindings for every tool used (Volatility3 is itself Python).
